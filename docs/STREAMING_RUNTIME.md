# Full-source recording, status and swerve analysis

Streaming stages S1–S3, a separate S4 incident-case format, service pacing and explicit fresh-attempt retries have local implementations, updated October 22, 2026. Executed qualification is recorded in [VALIDATION_CURRENT.md](VALIDATION_CURRENT.md). This path evaluates recording quality, source-reviewed Phoenix/SystemCore recorded status, swerve tracking and recorded steering dynamics through complete verified sources. Streamed incident capture/proof/candidate execution is documented in [REGRESSION_CASES.md](REGRESSION_CASES.md); broader scale/release qualification remains tracked in [STREAMING_ANALYSIS.md](STREAMING_ANALYSIS.md). Overall robot health remains not assessed.

## Normal operation

Normal small recordings keep the existing five-check automatic pipeline 7. When automatic selection reaches its existing row/scan resource limit, that immutable unavailable report is retained and a separate pipeline-11 job is queued. The indexing worker advances it in bounded turns even when no new import or plan revision arrives. Explicit historical pipeline 5/6/7 generation retains its old selector, inputs, output bytes and lack of stream scheduling. Explicit pipeline-8/9/10/11 scheduling uses a separate input contract and never constructs an empty tuple Evidence. Pipeline 8 retains its original quality-only interpretation, saved report bytes and reducer checkpoints.

Pipeline 9 retains the five-check order: quality, tracking, Phoenix status, SystemCore status and steering. Quality and the two status checks consume the full verified input; tracking and steering remain explicitly unavailable under this fixed historical policy. Pipeline 8 keeps its original quality result and four unavailable checks. Ordinary pipeline-7 reports remain usable, and a streamed result does not replace their saved bytes. A recorded warning is not a physical diagnosis.

Only completed byte verification, reducer completion and final evidence publication allow a saved report. Pending scans, canceled work, resource failures and missing inputs are never successful prefix analyses. Failures have fixed operator explanations; arbitrary exception text, private context and source paths are excluded from the progress API.

## Evidence and recovery

Catalog schema 12 installs retry requests and immutable terminal-attempt history as metadata only, retaining schema-10 stream tables and schema-11 ordered tracking work, percentile progress and revision fences. Its jobs, sources, chunks, checkpoints, persistent uniqueness and reservation tables are created without opening source artifacts. `StreamRunner` validates the supported format profile/extractor/importer/mapping tuple, source sizes and hashes, run/configuration/plan/component context and the structural chunking policy. Original import provenance takes priority over payload runtime labels: synthetic recordings stay synthetic.

Raw WPILOG, manifest and complete dataset bytes are verified in bounded phases. The new admission path does not call the legacy synchronous `Importer.read_manifest`, `iter_dataset` or `_check_dataset` helpers. Those helpers still exist on the older importer/catalog/pipeline-7 paths; this increment does not make the entire application startup or ingestion path incremental.

The selected evidence uses `stream-evidence-1`, framework `stream-analysis-1` and selection policy `full_source_scoped_rows_1`. Deterministic normalized JSONL chunks carry explicit source/line references and before-run, in-run, after-run or unscoped meaning. A versioned SHA-256 chain binds chunk bytes and range metadata. Full inventory generation is paged on disk rather than accumulated in a growing Python list. Chunk policy is part of input identity; runtime work-turn sizes, elapsed-time yields and storage allowances are not.

Chunk bytes are durably published before their metadata, reducer state and uniqueness contributions commit together. Checkpoints have exact hashes and chunk ordinals. On a fresh process or restored archive, raw/manifest verification restarts, the complete dataset byte prefix is rehashed from zero, and committed chunks are reconstructed and checked before new reducer contributions are accepted. A matching selected chain alone cannot validate changed unselected bytes. The same live byte hash continues through EOF; there is no serialized hash object or pickle checkpoint. Copied files may have new physical identities; their portable content pins stay exact and their new live identities are checked during reading.

Cancellation and same-generation resume remain internal worker APIs. The public operator action below always creates a fresh generation, retaining the previous terminal attempt; it never invokes internal resume or publishes a canceled prefix. Refreshing progress never retries analysis. Source changes require inspection rather than silently retargeting old evidence.

Normal turns retain no OS file handles. A failed close that leaves a handle open retains its strong owner; service cleanup remains pending and keeps the archive lease until actual closure. Connection/transaction ownership is explicit: writer operations reject caller-owned transactions before installing SQL callbacks or executing SQL. SQL budget exhaustion is isolated to the selected generation after rollback; unrelated database/schema failures remain visible.

## Recording-quality scope

Every admitted source is traversed through EOF. Quality counters, duration and findings are attributed only to the run's declared interval. Exact cycle payload time determines observation scope when the wire timestamp has lower precision. Source boundaries reset adjacent timing. A source that leaves the run cannot reenter it by regressing its clock and manufacture new in-run coverage.

Recording quality counts cycles/gaps, invalid or explicitly stale observations, recorded disconnected sources and clock coverage. Persistent uniqueness prevents a false connection observation reused by many samples from becoming many independent failures. Counts and decisions use all admitted data; retained supporting references share a 128-item budget, with exact omission totals. Full-source ordering/overlap/after-run hazards remain separate from in-run event attribution. Physical acquisition freshness and USB health stay unqualified.

## Recorded status scope and policy dispatch

Pipeline 9 pins `recorded-status@stream-recorded-status-1`, mapper `stream-cycle-mapper-1`, and distinct `stream-phoenix-status-1` / `stream-system-status-1` analyzer declarations. The composite checkpoint retains the unchanged recording-quality reducer alongside the two status accumulators. The worker dispatches by both saved pipeline version and exact reducer identity. A pending pipeline-8 job still resumes with `recording-quality@stream-recording-quality-1`; incompatible policy/reducer pairs are refused before advancing. No schema migration or rewriting of old reports/checkpoints is needed.

The mapper retains only required live fields and their original source, entry generation, record index and timestamp. Pre-run records can establish held state, while only in-run cycles contribute status counts and intervals. Source transitions, lifecycle controls, incompatible schemas, invalid observations and discontinuities prevent affected state from bridging incompatible evidence. After-run flags and counter updates are not new in-run warnings. Full-source ordering hazards remain separate qualification evidence.

Phoenix evaluates the source-reviewed diagnostics profile with exact recorded false-status decisions, deduplicated observation identities and bounded supporting references. SDK receipt/transmit timestamps, validity and ages remain recorded observations; physical acquisition time and native timestamp availability remain unqualified. SystemCore evaluates all 17 source-reviewed logger fields, exact true flags and canonical integer counter changes. Held states are counted separately from distinct source records. Counter increases/decreases do not establish physical event counts, resets or current/latched/cumulative fault semantics.

Voltage minimum/maximum and a stable time-weighted left-held mean are descriptive only. Adjacent compatible logger endpoints must advance by at most 250 ms; gaps and lifecycle/source boundaries do not become invented weighted coverage. No voltage fault threshold or physical freshness is introduced. Persistent uniqueness keys and bounded checkpoint state prevent full-run identities or example lists from accumulating in Python memory. Both converted checks retain explicit coverage limitations and bounded source-reference omission totals.

## Streamed tracking and exact percentiles

Pipeline 10 composes the unchanged status reducer with a separately pinned motion mapper and `stream-swerve-tracking-1` results. It carries compatible endpoints, integer duration/coverage, stable rescaled weighted moments and sustained errors across batches. Source, lifecycle, invalid inputs and gaps reset continuity. Its optional plan input selector is described in [AUTOMATIC_SWERVE.md](AUTOMATIC_SWERVE.md). No geometry is inferred from field names; scalar wheel velocity requires the confirmed radius and matching recorded configuration. Pipeline 10 rejects valid recorded build mismatches, but missing/invalid build aliases are a known admission gap; a human-declared plan build alone is not recorded build verification. Known-disabled terminal cycles can anchor run end without an empty command array poisoning otherwise valid enabled data. Unknown authority does not receive that exception.

Exact p95 uses persistent ordered samples and integer nanosecond weights: choose the first error for which `100*cumulative >= 95*total`, with contribution-sequence ties. No histogram or unweighted approximation replaces it. Contributions and totals commit with the chunk checkpoint. Bounded `work_validate` and `reducer_finalize` phases support restart; semantic prefix reconstruction rejects altered or rehashed percentile state. Sample-revision fences and post-finalization validation guard changes between passes. Final descriptor identity binds finalized work. Old pipeline-8/9 checkpoints and output bytes retain their original dispatch and numerical behavior.

Schema-11 backups include these metadata rows and verify their relation to reducer checkpoints; prior schema-10 snapshots retain their old validation path. Tracking examples share a 128-item allowance across all four modules. Saved reports state exact retained/omitted totals, and the browser distinguishes examples from complete traces. Metrics use all admitted intervals. Existing tuple baseline selections are explicitly incompatible with the new numerical/input policy; they are not silently reused as streamed baselines. Under this fixed pipeline-10 policy steering dynamics remains unavailable. Pipeline 11 adds that evaluator separately. Streamed incident export/proof now uses the separate format documented in [REGRESSION_CASES.md](REGRESSION_CASES.md).

A measured genuine-SIM late-run qualification traversed 440,809 source rows, including more than 402,741 rows before the run. It used a declared private run-pinned simulation context because the recording has no qualified wall clock; normal UTC plan association remains unavailable. Direct processing took about 55 seconds and 37 MiB process peak RSS. One turn reached 314 ms, so the cooperative 25 ms budget is not a hard latency bound. Those direct timings exclude the then-current 0.5-second service wait per worker tick and are not driver-station throughput guarantees. The subsequent scheduling implementation is described below. The tested stream stored about 393 MB of normalized spool for a 12.6 MB original, alongside its imported dataset. Source sharing/storage efficiency and physical load qualification remain open.

## Streamed recorded steering and strict source admission

Pipeline 11 retains the five-check order and adds `stream-recorded-steering-1` under composite `recorded-status-motion@stream-recorded-status-motion-1`. It pins `motion-work-2`, twelve ordered percentile targets, separate integer-nanosecond left-held/optimization-normalized numerics and the both-endpoints-enabled steering denominator. Tracking retains its own existing endpoint/numerical policy. This uses the existing schema-11 tables without a new migration. Explicit policies 5–10 keep their fixed contracts, checkpoints and saved reports.

`stream_motion_build_policy=recorded_build_and_configuration_required_1` requires valid exact recorded build and configuration hashes matching the selected plan before new motion contributions. Missing/invalid/different hashes invalidate the affected samples and prevent qualified tracking or steering results. Historical pipeline 10's missing-build gap is not silently rewritten. REAL steering remains descriptive recorded-state evidence and ignores acquisition freshness only; tracking still requires its independently qualified freshness policy.

Steering carries a bounded previous endpoint, pending command step, target/stability anchor, settle-band dwell, signed hysteresis side and sustained-error window across chunks. Source/lifecycle/payload discontinuities censor windows at their last eligible endpoint. The final endpoint can start a zero-duration step which is explicitly censored once in a persisted EOF subphase. It never becomes a zero settling-time success. Near-pi optimized wheel direction reversals are normalized independently of raw tracking errors before exact weighted p95 is stored.

The pinned availability policy separates hard source/identity/order/schema/build/configuration/runtime/authority failures from soft missing/invalid supported motion payloads. Both censor continuity. With enough declared coverage, valid recorded intervals still supply steering metrics and findings after ordinary payload gaps; soft reasons prevent an unqualified evaluated-no-finding result. Unknown error kinds fail hard. This does not loosen fixed pipeline-10 or pipeline-11 tracking admission.

Four modules share 128 retained steering reference copies and a 384 KiB canonical-reference allowance across traces, active windows, events and criteria. Event/interval/reference totals and omissions remain exact after the display allowance is spent. The browser groups seven measures, error plots and completed/censored response examples by module; it does not offer complete-trace navigation for omitted examples. Counts and metrics continue through the entire source. These allowances are separate from the overall checkpoint/SQL/disk limits.

## Resource policy and saved configuration

| Boundary | Default |
| --- | --- |
| Input work per turn | At most 4,096 records or 4 MiB, with a cooperative 25 ms elapsed check |
| Raw line / normalized selected row / deterministic chunk | 1 MiB each |
| Original import manifest | 4 MiB |
| Pinned sources per run | 128 |
| Stored supporting references per check | 128 shared across findings |
| SQL work allowance | Approximately five million VM steps |
| Conservative catalog-plus-stream disk allowance | 8 GiB |
| Free-space reserve | 2 GiB |
| Pipeline-10/11 work WAL allowance | 256 MiB |
| Pipeline-10/11 transaction headroom | 16 MiB |

The elapsed check is cooperative. A single file operation, fsync, atomic chunk/reducer transaction or metadata operation can exceed it; it is not a real-time deadline. The service uses the distinct pacing policy below. Direct active-processing benchmarks exclude service waits and therefore are not service completion times or driver-station load guarantees.

The disk allowance includes the entire catalog SQLite page allocation plus reserved stream files. It intentionally overcounts unrelated catalog data instead of pretending that shared SQLite indexes have zero cost. Reservations are durable before writes and retain charges for unfinished or orphaned owned work. Uniqueness/index growth is checked before reducer checkpoint commit. Existing large catalogs may require a larger allowance even before their first stream. Pipelines 10 and 11 additionally check WAL use and reserves transaction headroom before writes. These are cooperative admission and growth checks: a transaction can exceed the headroom before detected growth is rolled back. They are not OS-enforced peak-disk limits. No automatic evidence deletion or retention policy is added.

The saved private hub configuration accepts `stream_max_spool_bytes` (default 8589934592; 1 MiB–1 TiB) and `stream_min_free_bytes` (default 2147483648; 0–1 TiB), as strict integers. Despite the historical field name, the first value is the conservative catalog-plus-stream allowance described above. Edit the existing configuration and restart the hub to change admission limits; keep its archive/source profile unchanged. Raising an allowance does not qualify disk capacity, performance, freshness or a failed job for automatic retry.

## Service scheduling

The local worker separates one bounded stream turn from periodic import/retry/catalog maintenance. Direct `Pipeline.tick()` callers retain their existing combined behavior. The service opts into separated advancement, keeping maintenance due 0.5 seconds after completion and coalescing missed deadlines rather than replaying catch-up bursts. Extra stream turns do not repeat folder/pull import, retry and catalog scans on every iteration.

For pending/verifying/running/ready work, the next eligible turn waits at least 25 ms and three times the previous stream turn's elapsed wall time, targeting a 25% stream-work duty fraction. This is a pacing target, not an OS CPU quota or whole-service CPU percentage. Faster turns require explicit `OfflineSource` or fresh cached known-disabled status; enabled/stale/unknown status and operator Pause retain the baseline 0.5-second pacing. A status change revokes an already scheduled fast deadline before the next turn. These checks schedule local work only: they make no new robot requests and grant no remote transfer permission.

Idle/failed/canceled-only work uses the baseline wait. Waits remain interruptible by stop; current synchronous work must return before cleanup can complete. Runner/database/archive ownership stays held through actual handle closure. Periodic imports, run rebuilds and some finalization operations can still take substantial time; neither this scheduler nor a nominal 25-ms work allowance makes them hard real-time. Shared-source traversal, normalized storage expansion and driver-station load qualification remain open. Actual-service before/after qualification, including waits, is recorded in [current validation](VALIDATION_CURRENT.md); direct reducer measurements above must not be substituted for that measurement.

## Explicit fresh-attempt retry

The selected run offers **Request fresh analysis attempt** for an unpublished canceled stream, or one failed with `stream_free_space_unavailable` / `stream_spool_resource_limit`. Address free space or the saved storage allowance first. Source/hash/schema/checkpoint/inventory errors require inspection and stay ineligible. Active and published attempts cannot be retried here. This action processes archived local evidence; it does not download from the robot or alter source files.

`POST /api/v1/runs/<run>/streams/<stream>/retry` requires the existing local request protections, an active indexing worker and a strict body containing `request_id`, `stream_id`, `expected_generation`, `expected_state` and `expected_updated_utc_ns`. The generation and timestamp are canonical decimal strings over HTTP. The UUID and exact attempt pins produce a durable deduplicated receipt; conflicting or stale requests are refused. HTTP queues metadata only. It never constructs a runner or reads source artifacts. An uncertain browser response reuses the request ID; refresh is GET only.

The existing owned pipeline claims the request only after runner resources actually close. One transaction preserves the complete terminal job and request/source linkage, resets the current job to generation N+1 and creates copied exact source pins and an empty initial reducer checkpoint. Old chunks, checkpoints, uniqueness/work rows, reservations and files stay retained. Semantic stream ID, run, context, policy/reducer and structural chunking pins stay exact. A fresh attempt verifies original/manifest/dataset bytes from zero and never reuses the previous reducer result. Duplicate claims or restart cannot create a second generation for one request. Request receipts distinguish pending, running, completed, failed and superseded; failure does not schedule another retry.

Progress shows the current generation separately from up to three latest previous attempts and three latest request receipts, with exact retained totals. Unavailable projections retain unknown totals. This bounded live view is not complete immutable-history navigation. The protected local POST rechecks all pins even if the displayed button is stale. Saved report identities/bytes and historical fixed policies 8–11 remain unchanged.

All retained generation reservations remain charged to the catalog-plus-stream allowance. Retry is not a storage reclamation tool. Schema-12 coherent backup verifies history/request/child lineage and historical chunks, owner markers, inventories and retained reserved partials. Partials are quarantined evidence and never reusable reducer input. An over-reservation file is rejected. Schema-10/11 backups retain their original verification path; rollback requires restoring the pre-upgrade backup with the old release, not opening schema 12 with old code. Actual migration, browser and release qualification are recorded in [current validation](VALIDATION_CURRENT.md).

## Investigation and backup

Selected runs show a separate Full-log analysis progress section with source counts, exact byte/row counters, replayed bytes and saved-report availability. Read-only `/api/v1/runs/<id>/stream-progress` queries bounded SQLite metadata only; it never constructs a runner, scans artifacts, installs schema or repairs work. Live pages default to five jobs (maximum 20) and may shift as new jobs arrive. They are explicitly not immutable history snapshots. Missing/corrupt/budget-exhausted progress returns unavailable with unknown totals. Exact counters/timestamps use decimal strings, including values beyond JavaScript's safe integer range. Failed refresh clears live progress claims while preserving separately saved report and note evidence.

Coherent backups preserve source originals/datasets/manifests, exact committed chunks, ownership markers, final inventories and all resumable metadata/uniqueness/reservation rows. Restoring partially completed work into a fresh root and connection re-verifies it before continuing. Actual generated-data integration reproduced the identical final selection chain and full saved report after that restore.
