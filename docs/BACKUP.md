# Backup and restore

October 7 independent review strengthened exact inventory verification: a generation with unlisted physical files/directories, including SQLite sidecars or reused restore-staging leftovers, is rejected. Linked temporary outputs, locks, staging images and restore markers are rejected before opening. Focused synthetic tests: 20 passed; one symlink creation case was explicitly skipped because this Windows account lacks that privilege. Independent external-media and power-loss qualification remain required.

T19 provides an opt-in local CLI and independent service worker for coherent, verified archive generations. It does not configure an external destination automatically, contact a robot, remove source files, or prune generations.

Run from the hub checkout (Python 3.10 or newer):

```powershell
python -m robot_test_hub.backup create --data-dir C:/Team/hub-data --destination E:/Team/hub-backups --generation practice-2026-10-04
python -m robot_test_hub.backup status --data-dir C:/Team/hub-data --destination E:/Team/hub-backups
python -m robot_test_hub.backup verify E:/Team/hub-backups/practice-2026-10-04
python -m robot_test_hub.backup restore E:/Team/hub-backups/practice-2026-10-04 --destination C:/Team/restored-hub
```

Paths above are examples, not configured user locations. The backup destination must be disjoint from the source: neither may contain the other. Generation identifiers use letters, digits, underscores and hyphens. Commands print JSON; failed commands return exit status 1 with an exception-class error code rather than arbitrary exception text.

`create` first stages a SQLite online backup under `<data-dir>/exports/backup-jobs/<generation>/image/`. SQLite's backup API includes committed WAL changes coherently. The frozen snapshot uses a standalone database with DELETE journal mode; verification opens that image immutable and read-only. Database integrity, foreign-key relationships, supported schema version and required tables are checked. The live catalog is neither migrated nor edited by the command.

The catalog snapshot pins:

- Completed collector originals in `archive/`, checked against their expected hash and size.
- Importer originals and successful derived datasets/manifests, checked against their recorded hashes and sizes.
- Committed partial prefixes, checked against checkpoint offset and digest. Appended bytes beyond that offset are excluded. A partial already renamed to a final archive can supply the same pinned prefix.
- Quarantine files in `partial/*.invalid` and `quarantine/`, preserved with an explicit quarantine role. Identity-conflict rows remain terminal in the restored catalog; quarantined bytes never become verified or resumable bytes.
- The complete catalog, including annotation revisions, clock/run records, jobs, review history and pause settings.

Only supported catalog file contracts are copied. Unreferenced raw/derived files, open camera recordings, browser IndexedDB, diagnostics, ownership files, and arbitrary files beside the catalog are outside this generation's scope. Missing or changed referenced artifacts fail the generation visibly. Credentials and arbitrary configuration files are never discovered or copied. For a manual generation, include the hub's validated, secret-free configuration with `--config path/to/hub-config.json`; the copy is `hub-config.json`. Scheduled service generations include the effective supported hub configuration automatically. Configuration is pinned before capture and retained across retries. Its original data-directory value remains historical configuration: review paths explicitly before using it for a restored service.

A canonical JSON manifest sorts file paths and records schema, generation identity, fixed capture time, file roles, SHA-256, sizes and checkpoint-prefix flags. The same generation reuses its original SQLite snapshot, manifest and staged bytes. It does not drift with later notes or catalog changes. Once the local image verifies, replication copies it to `<destination>/<generation>/`. The destination manifest is published last and the full generation is independently read and verified before the local job reports `complete`.

An interrupted capture or disconnected destination leaves durable job state and staging. Repeat the original `create` command with the same generation and destination to retry. Existing files with different hashes are preserved and cause an error; a retry does not overwrite them. Local staged images and every external generation are retained. Stage and replica therefore consume extra storage; cleanup and retention are a separate, unimplemented policy. Destination replication does not require unchanged original files after the complete staging image exists. Local and destination locks prevent competing generation writers; the collector may continue running while SQLite snapshots and committed prefixes are captured.

`status` reports each generation's capture/completion timestamps, state, file/byte counts, manifest digest and redacted error class. The generation's capture time identifies its evidence age, independently of transfer/import/report status.

The service worker is disabled by default (`backup_destination: null`). To opt in, set an explicit disjoint `backup_destination` in the versioned hub configuration. `backup_interval` defaults to 3600 seconds between capture starts; `backup_retry` defaults to 60 seconds after an error. Both are finite positive seconds, capped at 86400. No external path is configured by the repository. On service startup, the worker resumes the oldest noncomplete generation for that configured destination before starting a new generation. Failed external copies keep their pinned local image. Switching a destination does not redirect old queued generations. Existing completed generations remain immutable and retained.

Backup runs on its own worker. Collector pause/status/API access remain independent of snapshot and replication work. Stop is checked during SQLite backup pages and between artifacts. A blocked filesystem operation can still delay shutdown; the service retains ownership on its ordinary shutdown timeout until all workers finish. Real storage/DS resource contention requires separate measurement.

`GET /api/v1/backup`, `/api/v1/status`'s `backup` property, and redacted diagnostics expose cached worker state, pending generation count, last verified generation/capture/completion time, capture age, and retry/error state. The Transfers page displays disabled, capturing/replicating, retry waiting and last verified capture age. The API does not enumerate external paths or scan backup files on the HTTP thread. Capture age becomes unknown if the wall clock precedes the capture. This status does not imply continuous source collection or an independently qualified destination.

`restore` verifies every file, catalog integrity and catalog-to-manifest reference before publication. It requires an explicitly empty or absent destination disjoint from the selected backup. It uses sibling staging and a lock specific to the destination, rechecks emptiness, and does not merge into an existing archive. An absent destination publishes by directory rename. An already existing empty directory receives the already verified top-level entries; an interruption in that final publication can leave a nonempty destination, which is intentionally rejected on a later attempt. Preserve that directory and restore again to a new empty destination. Staging is retained. The restored raw/derived hashes, catalog relationships, revisions and committed prefixes match the captured generation. Future normal collector recovery still applies its usual checkpoint and permission rules.

The manifest detects accidental corruption; it is not a signed authenticity assertion. External storage availability, capacity, device identity, backup age and actual failure independence need operational checks. A different folder on the same disk is not an independent backup. Every result explicitly reports `failure_domain_qualified: false`; no path heuristic substitutes for a team-reviewed separate device or failure domain.

Validation: `python -m unittest discover -s tests -p test_backup.py -q` passes **14 tests** on Windows Python 3.10.7. These cover online WAL snapshots, note/pause relationships, raw and derived hashes, committed prefix truncation, latched quarantine, interrupted capture/replication retry, missing/corrupt files, unsupported paths and extra files, catalog structure/reference corruption, immutable generations/configuration, retained generations, clean restore, and redacted CLI errors. Five additional scheduler/service tests cover opt-in defaults, interval and retry scheduling, persisted restart recovery, cached HTTP backup status, independent pause, and ownership retention during a blocked local backup. The final integrated `python -m unittest discover -s tests -q` run passed **221 tests**, with one optional Alpha 7 bridge qualification test skipped. The newest qualified mapping selection and unsupported mapping regressions are included in that passing run. Browser verification checked disabled and configured/verified backup panels against temporary loopback demo archives. Temporary servers were stopped. Tests use two temporary directories on the same computer; independent failure-domain, real external-media interruption, season-scale capacity and power-loss durability have not been qualified.
